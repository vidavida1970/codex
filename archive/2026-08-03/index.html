결과가 나쁠 때마다 “좀 더 구체적으로”라고 덧붙이나요? 먼저 고칠 것은 결과가 아니라 일을 시킨 방식입니다.

오늘의 학습목표
기존 프롬프트·실패 결과·평가기준을 ChatGPT에 함께 주고, 실패 원인을 진단한 프롬프트 v2와 재시험 계획을 만든다.

핵심 개념 1분

메타프롬프트는 결과물을 직접 요청하는 지시가 아니라, 더 나은 프롬프트를 설계·비평·개정하도록 요청하는 지시입니다. 핵심은 “완벽한 프롬프트를 써줘”가 아니라 증거가 있는 개선 루프입니다.

증거기존 프롬프트와 실패 결과무엇이 잘못됐는지 실제 출력에서 문제 문장을 찾습니다.
기준평가표와 통과 조건대상 적합성·근거·실행성·형식처럼 성공을 판단할 기준을 줍니다.
개정원인별 수정과 변경 이력왜 바꿨는지 설명하고 고정 규칙·변수·빈값 규칙을 정리합니다.
재시험같은 입력으로 v1·v2 비교조건을 바꾸지 않고 다시 실행해 점수가 실제로 나아졌는지 확인합니다.

잘못된 사용법과 개선

BAD

“최고의 프롬프트로 고쳐줘”

실패 출력·목적·평가기준이 없으니 문장만 길어집니다. 수정 이유도 시험 방법도 남지 않습니다.

BETTER

실패 증거로 v2 설계

기존 지시와 나쁜 출력에서 결함을 찾고, 기준별 원인·수정안·테스트를 연결합니다. 불명확한 정보는 먼저 질문하게 합니다.

애드아이티 실무 예시 · 공공기관 제안서 요약문

실패: “지역관광 홍보전략을 500자로 요약”했더니 모든 지자체에 통하는 일반론과 근거 없는 기대효과가 나옴.

메타프롬프트 입력: RFP, 대상 관광객, 승인 예시, 실패 출력, 심사기준을 함께 제공.

개정 결과: 근거 자료 우선순위, 대상별 메시지, 금지 표현, 500자 구조, 수치 빈값 규칙을 포함한 v2와 변경 이유를 받음.

OpenAI: 측정→후보 생성→전체 검증의 반복 개선

사실과 강사 해석

확인된 사실: OpenAI가 공개한 기술 업무 흐름과 두 성과 지표. 강사 해석: 제안서 프롬프트도 같은 구조로 운영할 수 있습니다. 실패 출력을 측정 자료로 삼고, v2 후보를 만든 뒤 전체 심사표로 재검증합니다. 국내의 메타프롬프트 성과를 수치로 입증한 공개 실무 사례는 확인하지 못해 꾸며 넣지 않았습니다.

복사형 실전 프롬프트

[역할] 너는 프롬프트 품질검수자다. 결과물을 새로 쓰기 전에 기존 지시가 왜 실패했는지 증거로 진단하고 개선안을 설계하라. [업무 목적] [누가 무엇을 위해 사용할 결과물인지] [기존 프롬프트 v1] [붙여넣기] [실패한 결과] [붙여넣기] [평가기준과 통과 조건] 1. [기준 1]: [통과 조건] 2. [기준 2]: [통과 조건] 3. [기준 3]: [통과 조건] [근거 자료] [파일·원문 링크·승인 예시] [수행] 1. 실패 결과에서 기준별 결함 문장을 인용하지 말고 짧게 지목한다. 2. 결함의 원인을 `누락·충돌·모호·형식·근거`로 분류한다. 3. 정보가 부족하면 개선 전에 확인 질문을 최대 5개 한다. 4. 각 원인과 직접 연결된 프롬프트 v2를 작성한다. 5. `변경 항목 | 변경 이유 | 기대 효과 | 검증 방법` 표를 만든다. 6. v1·v2를 같은 입력으로 비교할 테스트 3개를 제안한다. [제약] - 근거 자료에 없는 사실·수치·인용은 만들지 않는다. - 효과를 보장하지 않는다. - 길이를 늘리는 것 자체를 개선으로 판단하지 않는다. - 평가기준과 연결되지 않은 규칙은 추가하지 않는다. [출력 순서] 진단표 → 확인 질문 → 프롬프트 v2 → 변경 이력 → 재시험표 지금은 결과물을 작성하지 말고 프롬프트 개선안까지만 제시하라.

자주 하는 실수
