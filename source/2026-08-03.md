# DAY 19. 메타프롬프트로 프롬프트 자체를 개선하기

**발행일:** 2026년 8월 3일  
**과정:** ADDIT | ChatGPT로 성공하기 40일 과정

## 10초 훅

결과가 나쁠 때마다 “좀 더 구체적으로”라고 덧붙이나요? 먼저 고칠 것은 결과가 아니라 일을 시킨 방식입니다.

## 오늘의 학습목표

기존 프롬프트·실패 결과·평가기준을 ChatGPT에 함께 주고, 실패 원인을 진단한 프롬프트 v2와 재시험 계획을 만든다.

## 핵심 개념 1분

메타프롬프트는 결과물을 직접 요청하는 지시가 아니라, 더 나은 프롬프트를 설계·비평·개정하도록 요청하는 지시다. 핵심은 “완벽한 프롬프트를 써줘”가 아니라 증거가 있는 개선 루프다.

1. **증거:** 기존 프롬프트와 실패 출력에서 문제를 찾는다.
2. **기준:** 대상 적합성·근거·실행성·형식의 통과 조건을 준다.
3. **개정:** 원인별 수정과 변경 이력을 남긴다.
4. **재시험:** 같은 입력으로 v1·v2를 비교한다.

## 잘못된 사용법과 개선

- 잘못된 요청: `최고의 프롬프트로 고쳐줘.`
- 문제: 실패 출력·목적·평가기준이 없어 문장만 길어진다.
- 개선: 기존 지시와 나쁜 출력에서 결함을 찾고, 기준별 원인·수정안·테스트를 연결한다. 불명확한 정보는 먼저 질문하게 한다.

## 애드아이티 실무 예시

공공기관 지역관광 제안서의 500자 요약이 일반론과 근거 없는 기대효과로 채워졌다고 가정한다. RFP, 대상 관광객, 승인 예시, 실패 출력, 심사기준을 함께 제공해 근거 자료 우선순위·대상별 메시지·금지 표현·500자 구조·수치 빈값 규칙이 들어간 v2와 변경 이유를 받는다.

## 오늘의 실제 사례

**기관:** OpenAI  
**적용 시점:** 2026년 7월 29일 공개  
**문제:** 대규모 추론 환경의 부하 불균형, 비효율적 연산, 큰 설정 탐색 공간을 개선해야 했다.  
**기능·업무 흐름:** 생산 환경 측정 → 큰 격차 식별 → GPT-5.6 Sol과 Codex로 후보 생성·실험 → 전체 시스템 개선 여부 검증.  
**공개 결과:** 프로덕션 커널 개선을 포함한 노력으로 엔드투엔드 서빙 비용 20% 감소. 별도의 draft model 개선에서는 토큰 생성 효율 15% 이상 증가.  
**재현 포인트:** 현재 상태를 먼저 측정하고, 변경 후보를 여러 개 만든 뒤, 동일 기준으로 전체 결과를 다시 검증한다.  
**원문:** [How GPT-5.6 fuses frontier intelligence with frontier efficiency](https://openai.com/index/gpt-5-6-frontier-intelligence-efficiency/)

확인된 사실은 OpenAI가 공개한 기술 흐름과 성과 지표다. 제안서 프롬프트에도 실패 출력을 측정 자료로 삼아 v2를 만들고 전체 심사표로 재검증할 수 있다는 부분은 강사의 실무 해석이다. 국내에서 메타프롬프트 효과를 수치로 검증한 공개 사례는 확인하지 못했다.

## 2분 따라 하기

1. DAY 18에서 만든 업무 템플릿 v1과 가장 나빴던 출력 하나를 준비한다.
2. 평가기준 3개와 각 통과 조건을 한 줄씩 적는다.
3. 아래 메타프롬프트로 원인 진단·v2·변경 이력·시험안을 받는다.
4. 같은 입력으로 v1과 v2를 실행하고 세 기준의 점수를 비교한다.

## 복사형 실전 프롬프트

```text
[역할]
너는 프롬프트 품질검수자다. 결과물을 새로 쓰기 전에
기존 지시가 왜 실패했는지 증거로 진단하고 개선안을 설계하라.

[업무 목적]
[누가 무엇을 위해 사용할 결과물인지]

[기존 프롬프트 v1]
[붙여넣기]

[실패한 결과]
[붙여넣기]

[평가기준과 통과 조건]
1. [기준 1]: [통과 조건]
2. [기준 2]: [통과 조건]
3. [기준 3]: [통과 조건]

[근거 자료]
[파일·원문 링크·승인 예시]

[수행]
1. 실패 결과에서 기준별 결함을 짧게 지목한다.
2. 원인을 `누락·충돌·모호·형식·근거`로 분류한다.
3. 정보가 부족하면 개선 전에 확인 질문을 최대 5개 한다.
4. 각 원인과 직접 연결된 프롬프트 v2를 작성한다.
5. `변경 항목 | 변경 이유 | 기대 효과 | 검증 방법` 표를 만든다.
6. v1·v2를 같은 입력으로 비교할 테스트 3개를 제안한다.

[제약]
- 근거 자료에 없는 사실·수치·인용은 만들지 않는다.
- 효과를 보장하지 않는다.
- 길이를 늘리는 것 자체를 개선으로 판단하지 않는다.
- 평가기준과 연결되지 않은 규칙은 추가하지 않는다.

[출력 순서]
진단표 → 확인 질문 → 프롬프트 v2 → 변경 이력 → 재시험표

지금은 결과물을 작성하지 말고 프롬프트 개선안까지만 제시하라.
```

## 결과 체크 3문항

1. 모든 수정이 실제 실패 증거와 평가기준에 연결됐는가?
2. v2에 필요한 자료·제약·출력 형식·빈값 규칙이 명확한가?
3. 같은 입력과 같은 기준으로 v1·v2를 다시 비교했는가?

## 자주 하는 실수

- 실패 결과 없이 기존 프롬프트만 보여주는 것
- 모든 문제를 프롬프트 탓으로 보고 원자료 결함을 놓치는 것
- v2가 길어졌다는 이유로 더 좋아졌다고 판단하는 것
- 테스트 입력까지 바꿔 개선 전후를 비교할 수 없게 하는 것

## 오늘의 미션

DAY 18 템플릿 하나와 실패 출력 하나를 골라 프롬프트 v2를 만든다. 같은 입력으로 v1·v2를 실행하고 세 평가기준 중 몇 개가 개선됐는지 기록한다. 개선이 확인되지 않으면 v1을 유지한다.
