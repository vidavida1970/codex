# DAY 22. 팀 검수 결과를 프롬프트 개선 백로그로 연결하기

> 검수 실패는 지적이 아니라, 증거와 완료 조건을 갖춘 다음 개선 과제여야 합니다.

- 발행일: 2026년 8월 8일
- 진행률: DAY 22 / 40
- 다음 강의: DAY 23 검색 질문을 조사계획으로 바꾸기

## 10초 훅
검수표에 “실패”만 남기면 같은 문제가 반복됩니다. 실패를 증거가 있는 개선 과제로 바꿔야 품질이 누적됩니다.

## 오늘의 학습목표
DAY 21 팀 체크리스트의 실패를 증거·심각도·원인 가설·수정 범위·재시험 조건이 있는 프롬프트 개선 백로그로 전환한다.

## 핵심 개념 1분
개선 백로그는 희망 목록이 아닙니다. 실패 증거를 작은 수정 과제로 바꾸고 심각도·반복 빈도·수정 비용으로 우선순위를 정한 뒤 재시험 통과까지 추적합니다.

1. 증거: 실패 문장과 입력 조건을 재현 가능하게 남긴다.
2. 분류: 누락·충돌·모호·형식·근거·도구로 묶는다.
3. 우선순위: 심각도 × 반복 빈도 × 수정 비용으로 처리 순서를 정한다.
4. 종료: 담당·기한·수정 범위·통과 조건을 적고 재시험 통과까지 닫지 않는다.

## 잘못된 사용법과 개선
- 잘못: “다음에는 더 꼼꼼히”로 종료한다.
- 개선: 한 실패를 한 카드로 만들고 표적 테스트와 전체 회귀 테스트를 완료 조건으로 둔다.

## 애드아이티 실무 예시
| ID | 실패 증거 | 개선 과제 | 완료 기준 |
|---|---|---|---|
| B-01 | 원문 없는 기대효과 수치 생성 | 수치 출처 필드와 빈값 규칙 추가 | 누락·충돌 사례 모두 수치 생성 0건 |
| B-02 | RFP 표현을 확정 성과처럼 서술 | 사실·목표·제안 구분 태그 추가 | 검수자 2명이 동일 분류 |
| B-03 | 500자 제한 반복 초과 | 출력 전 글자 수 자체 점검 추가 | 대표 사례 6개 모두 500자 이내 |

## 오늘의 실제 사례
**Thrive Holdings·Crete·OpenAI — 당사자 공동 공개 사례**
- 적용: 2025년 말~2026년 상반기 공동 개발, 2026년 5월 27일 공개
- 흐름: 전문가 수정과 전체 처리 경로 기록 → 반복 실패 분류 → 평가 목표 → 범위가 정해진 Codex 과제 → 표적·회귀 평가
- 결과: 파일럿 신고서 7,000건, 세무 준비 시간 약 3분의 1 절감, 최대 97% 정확도, 처리량 약 50% 증가. 75% 필드 정확도 도달 신고 비율은 출시 시 25%에서 6주 뒤 86%로 상승
- 원문: https://openai.com/index/building-self-improving-tax-agents-with-codex/

## 2분 따라 하기
1. DAY 21 체크리스트에서 실패 항목 하나와 해당 출력 문장을 고른다.
2. 실패 유형·심각도·반복 빈도·영향받는 산출물을 적는다.
3. 프롬프트에서 바꿀 한 부분과 바꾸지 않을 부분을 구분한다.
4. 표적 테스트 1개와 전체 회귀 테스트 조건을 정해 카드로 저장한다.

## 복사형 실전 프롬프트
```text
너는 프롬프트 개선 백로그 관리자다.
[현재 프롬프트]와 [팀 검수 결과], [실패 입력·출력·기대 행동·실제 영향]을 근거로:
1. 실패를 누락·충돌·모호·형식·근거·도구 중 하나로 분류하라.
2. 원인 가설 최대 2개, 심각도·빈도·수정 비용을 판정하라.
3. 한 카드가 한 문제만 다루도록 수정 범위와 비범위를 정하라.
4. 표적 테스트와 전체 회귀 조건을 완료 기준으로 작성하라.
5. 즉시/이번 주/관찰/제외 중 우선순위를 추천하라.
출력: ID | 실패 증거 | 유형 | 심각도 | 빈도 | 원인 가설 | 수정 범위 | 비범위 | 담당 | 기한 | 표적 테스트 | 회귀 조건 | 우선순위
```

## 결과 체크 3문항
- 실제 실패 증거와 재현 조건이 있는가?
- 심각도·빈도·수정 비용으로 우선순위를 설명할 수 있는가?
- 표적 테스트와 전체 회귀 테스트가 완료 조건에 있는가?

## 자주 하는 실수
한 카드에 여러 문제를 묶기, 한 사람의 취향을 치명 결함으로 다루기, 원자료 문제를 프롬프트만 고쳐 해결하기, 회귀 묶음을 생략하기.
